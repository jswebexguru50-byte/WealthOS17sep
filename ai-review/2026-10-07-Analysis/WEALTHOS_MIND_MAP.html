WealthOS: how the modules fit, and where it stalls

Structure from graphify AST pass (1,383 nodes, 2,695 edges, 58 communities, 75 files) plus targeted reads. Red = critical for load time, amber = high, yellow = medium.

Bottleneck legend

  • B1
    Critical — One SQLite connection serialises everything (background recompute blocks foreground)
  • B2
    High — Coarse cache invalidation: any FIFO run wipes all dashboards + disk cache → next load is a cold full compute
  • B3
    Critical — buildDashboardPayload: ~25 serial awaits, unfiltered full-table reads (RealizedGains GROUP BY, all Transactions), JS-side XIRR; frontend waterfall
  • B4
    Critical — No ANALYZE / optimize; 36 redundant or duplicate indexes (3 identical on HistoricalPrices); bloats a 3.4 GB file
  • B5
    High — Per-row awaited writes with no transaction (34 sites) — each is a WAL commit
  • B6
    Medium — Giant components, inline styles, no memoisation — slow render after data arrives
  • B7
    Critical — createPersistentBackup() fires after every successful dbRun: full 3.4 GB file copy ≤ every 10 min (I/O storm, also not a consistent snapshot)
  • B8
    Medium — God files / routers, import cycle database↔xirr↔fifoEngine — slows change, risks load-order bugs

What happens on a slow first load

  1. Browser opensindex.html + entry chunk (theme modal pulled in by main.tsx)
  2. GET /api/dashboardcache hit < 3 min = instant. Miss → DashboardDiskCache read (recompute is then triggered every time because ts=0) → else cold compute
  3. Cold computegetAllowedPortfolios → FX → holdings join → bank/FD → symbols → tickers → realized gains (whole table) → all txns for asset XIRR → cash/PMS → dividends → snapshot (~25 awaits, one connection)
  4. Then in parallel/api/dashboard/xirr and /api/growth-history (2,868-line generateImmediateGrowthHistory) queue behind the same connection
  5. Meanwhileevery write triggers backup copy (3.4 GB); any FIFO completion clears all caches

Caveat: static analysis only. No runtime profile or row counts were available (the 3.4 GB database was not readable from here), so run the diagnostics script in the report to confirm ranking.
