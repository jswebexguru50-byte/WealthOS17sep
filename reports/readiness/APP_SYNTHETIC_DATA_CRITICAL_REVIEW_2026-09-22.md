# Critical review: synthetic and unverified application data

Review date: 2026-09-22. Scope: production server routes, services, export paths, and separately launched data jobs. This is a source-code and database inspection, not a claim that every route was exercised end to end. Test fixtures and comments about preventing fabrication are excluded from the findings below.

## Executive finding

Several user-facing functions can turn missing source data into plausible prices, financial ratios, confidence scores, portfolio curves, or reports. The FERE ledger is the clearest example: 3,559 rows exist, but the worker that populated this table computes key inputs from fixed constants and estimated proxies. The local financial statement table has 2,295 rows across 344 identifiers, but zero populated `period_date` values, only 25 populated sales values, and cash-flow values for 49 identifiers. It cannot support a verified full-universe Beneish, Altman, Piotroski, Sloan, and CCC calculation today.

## FERE data path and recovery specification

Current path: separately launched FERE worker reads `MasterTickers`, one `DailyOHLCV` row, and at most one `FundamentalSnapshots` row; it fills missing values with constants, computes proxy ratios, and writes `FEREEnrichedLedger`. The API presents those rows as a filing-backed forensic deep dive. The general acquisition daemon has another fixed-quarter fundamental provider; it is not a valid replacement.

Required path: obtain dated exchange/MCA filing documents and structured statement rows; retain document URL, filing date, period end, standalone/consolidated flag, units, field path, and extraction status. Normalize balance sheet, P&L, cash flow, receivables, inventory, payables, depreciation, debt, shares, and promoter pledges by ISIN and period. Compute each score only when all required numerator/denominator and prior-period fields exist. Store each formula version, input IDs, source hashes, and calculation timestamp. Mark partial metric coverage separately from a complete FERE verdict. Reconcile against a second source or manual review for material conflicts. Refresh only when a new filing is available; stale or failed fetches must retain the last verified value with its date, not manufacture a fresh score.

## Immediate order of work

1. Keep the synthetic acquisition daemon, order arming fallback, and optimistic report defaults away from actionable decisions.
2. Build a verified FERE input ledger and source-specific adapters, then recompute only fully supported metrics.
3. Replace scanner and opportunity defaults with explicit missing-data outcomes.
4. Remove random or constant portfolio/FX/Excel fallbacks and expose data freshness in the UI.
5. Add regression checks that fail if a production route calls a synthetic generator or turns missing required inputs into a positive score.

## Review limits

The repository has many more references to “mock,” “synthetic,” and numeric defaults. Some are test fixtures, parameter defaults, simulations explicitly labeled as such, or defensive code. The table above covers confirmed user-facing or separately runnable paths inspected in this pass. Every remaining production service should be traced from its route to its source and persistence layer before claiming the entire app is free of artificial data.
